# 43. Use ghostty-web for NSH terminals

User request (2026-11-12): use [coder/ghostty-web](https://github.com/coder/ghostty-web) instead of xterm for NSH terminals. This is a renderer replacement for the existing user-owned terminal dock on NSH web and macOS, not a new terminal service. Mobile remains without a terminal dock. Keep the TUI and NSH desktop/web behavior aligned; do not change the TUI's renderer or its separate xterm-based screenshot harness merely because NSH changes engines.

## Today

- Core owns the PTY, replay, attachments and controller authority; the shared client contract is in [docs/terminals.md](../docs/terminals.md). The TUI parses locally with `vt100`.
- NSH embeds `src/terminal-page.html` in a `WebView` (`src/ui/terminal.tsx`). The page bridges input, resize, focus, output, selection and control to NSH. `scripts/gen.py` inlines xterm, the fit addon, CSS and licenses into generated `src/gen/terminal-page.ts`. Dependencies are pinned in `package.json` and `package-lock.json`.
- `e2e/terminal-page.test.mjs`, `e2e/terminal-keymap.mjs` and `e2e/terminal-core-smoke.mjs` depend on xterm APIs or DOM selectors. Native key routing also depends on the macOS host; see `nexus-nsh/README.md`.
- Upstream describes ghostty-web as an xterm-compatible API backed by a Ghostty WASM parser, initialized asynchronously with `await init()`. Compatibility is a goal, not proof that every API or host environment used here works. Upstream is MIT licensed.

Test the real iframe/WebView origin, CSP and WASM loading restrictions; choose an embedded or locally served asset approach that works in both. Surface initialization failures visibly, never announce `ready` before the terminal is usable, and handle messages arriving during initialization without losing or reordering them. If a host cannot support this safely, document the blocker rather than silently falling back to xterm.
